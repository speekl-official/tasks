A handful of ideas carry the whole system. Once these land, the
[command reference](/docs/reference/commands) is mostly mechanical. The normative text
for each lives in the [specification](/docs/spec); this page explains them.

## The tree

`.tasks/` is discovered by walking up from the current directory, git-style: **nearest
wins, no merging** with a tree further up. Each package in a monorepo that has its own
`.tasks/` is its own tree. `-C <dir>` starts the search somewhere else, which is how a
session working in a secondary worktree addresses the tree of the main checkout.

Everything the CLI knows is read from files on disk on every invocation. There is no
cache and no daemon, so editing a task body by hand, or pulling someone else's branch,
takes effect immediately. Every change to a tree happens under one lock,
`.tasks/.locks/tree.lock`, and re-reads what it depends on inside it.

## Tasks are directories

A directory under `.tasks/` that contains a file named `task.md` is a **task**. The
manifest holds the definition — frontmatter the CLI owns, a body you write — and the rest
of the directory is the task's **workspace**:

<Files>
  <Folder name="token-schema" defaultOpen>
    <File name="task.md" />
    <File name="state.md" />
    <File name="design.md" />
    <File name="plan.md" />
    <File name="log.md" />
    <Folder name="screenshots" />
  </Folder>
</Files>

| File        | Holds                                                    | Written                                           |
| ----------- | -------------------------------------------------------- | ------------------------------------------------- |
| `task.md`   | The definition and acceptance; later inputs in `## Notes` | Body by you; frontmatter by commands              |
| `state.md`  | Where the work stands now: done, verified, open, next    | Replaced in full, through `tasks state`           |
| `design.md` | Decisions and why; rejected alternatives                 | By you, in place                                  |
| `plan.md`   | How: steps, files, verification                          | By you, in place                                  |
| `log.md`    | What happened, who, when                                 | Appended by the CLI; never edited                 |

Only `task.md` is required. Anything else in the directory — a `screenshots/` folder, a
scratch script — is workspace content the CLI never parses or rewrites.

## Ids are paths

A task's **id** is its path relative to `.tasks/`: `auth-rework/token-schema`. Every
segment matches `^[a-z0-9][a-z0-9-]*$`. There is no `id` field to drift from the
filename, and the namespace never fills up: `auth-rework/tests` and `billing/tests`
coexist. A task's **name** is its last segment; its **title** is the first `# ` heading
of its body.

On the command line, any **unambiguous suffix** works: `tasks show token-schema` finds
`auth-rework/token-schema` when no other id ends in `/token-schema`. Two candidates are a
usage error that names both. References are always stored as full paths.

Moving a task changes its id and the ids beneath it, so it goes through
`tasks move`, which rewrites every reference to them — never through `mv`.

## Groups, epics and children

A directory without `task.md` is a **group**: organizational only, no status, any depth.
The **parent** of a task is its nearest ancestor directory that is a task; groups in
between do not break parenthood. A task with children is informally an **epic**.

Children are **parts of the parent's deliverable, never phases of its lifecycle.**
Planning, executing, reviewing and approving a task happen on the task itself — in
`plan.md`, `state.md`, and through a `handoff` to the approver. A child named `plan`,
`review` or `verify` is a modelling error.

```txt
.tasks/
  auth-rework/            task — the epic
    task.md
    design.md             the epic's decisions live with the epic
    token-schema/         child task
    wire-refresh/         child task
  2026-q4/                group — no task.md
    migrate-logging/      task, parent is the root
```

Creating a task at the path of an existing group turns the group into a task, and the
tasks beneath it become its children.

## The lifecycle

The statuses are a **fixed vocabulary**: they read the same in every repository, grep
without configuration, and need no legend.

| Status        | Fact recorded                                                       | Open? |
| ------------- | ------------------------------------------------------------------- | ----- |
| `BACKLOG`     | Not scheduled.                                                      | open  |
| `TODO`        | Scheduled, not started.                                             | open  |
| `IN_PROGRESS` | Being worked right now; a claimant is recorded.                     | open  |
| `PAUSED`      | Started, not being worked: waiting for a dependency, a person, or free hands. | open  |
| `DONE`        | Finished.                                                           | resolved |
| `CANCELLED`   | Explicitly decided not to do.                                       | resolved |

Each command names the fact it writes:

| Command               | From                    | To                                                            |
| --------------------- | ----------------------- | ------------------------------------------------------------- |
| `schedule`            | `BACKLOG`               | `PAUSED` when `state.md` exists, else `TODO`                  |
| `defer`               | `TODO`, `PAUSED`        | `BACKLOG`                                                     |
| `claim`               | `BACKLOG`, `TODO`, `PAUSED` | `IN_PROGRESS`                                            |
| `pause`               | `IN_PROGRESS`           | `PAUSED` — needs a `state.md` and a message                   |
| `handoff <actor>`     | `IN_PROGRESS`           | `PAUSED`, assigned to the actor — needs a `state.md` and a message |
| `release`             | `IN_PROGRESS`           | `TODO` — only when no `state.md` exists                       |
| `done`                | any open                | `DONE` — needs a message; the gates must be satisfied         |
| `cancel`              | any open                | `CANCELLED` — needs a message                                 |
| `reopen`              | `DONE`, `CANCELLED`     | `BACKLOG` under a `BACKLOG` ancestor, else `PAUSED` with a `state.md`, else `TODO` — needs a message |
| `assign` / `unassign` | any open                | unchanged; sets or clears `assignee`                          |
| `priority <level>`    | any open                | unchanged; sets `priority`                                    |

A single `PAUSED` covers every kind of waiting, because _what_ is waited for is recorded
elsewhere: a task in `depends_on`, a person in `assignee`, or nothing — free hands.
`release` exists only for a claim that produced nothing; work that produced anything is
paused, because returning half-done work to `TODO` would be a lie.

**Claimed** and **assigned** are different facts. The claimant (`claimed_by`) is working
on the task right now. The assignee is who must act on it next — a review, an approval, a
deploy only one person can run — and who alone may transition it while nobody holds a
claim. Authority flows down the tree: the assignee of an epic may also transition the
assigned tasks beneath it.

## Situations, not statuses

The status is what a task says about itself. The **situation** is what the tree says
about the task: one word computed from its status and its surroundings, chosen as the
first row that holds.

| Situation       | When                                                       |
| --------------- | ---------------------------------------------------------- |
| `done`, `cancelled` | resolved                                               |
| `working`       | a claimant is recorded; shown with its liveness            |
| `parked`        | `BACKLOG` with started work (a `state.md`) at or beneath it |
| `backlog`       | `BACKLOG` without started work                             |
| `held by X`     | an ancestor X is claimed or assigned                       |
| `waiting for X` | `PAUSED` with an assignee                                  |
| `assigned X`    | an assignee, not `PAUSED`                                  |
| `blocked by X`  | an unsatisfied `depends_on` reference                      |
| `closable`      | a parent whose children are all resolved                   |
| `open N/M`      | a parent with open children: `N` of `M` resolved           |
| `ready`         | free and unblocked                                         |

Overviews — `ready`, `mine`, `list`, `tree` — show the situation and, after it, any
other condition that holds as a secondary label: `started`, `blocked by A (cancelled)`,
`active` for a parent with a task in progress beneath it, a priority other than
`normal`, the claim's liveness, the assignee. They never show the stored status; `show`,
`resume`, the JSON `status` field and the file do. So an epic whose child is being
worked reads `open 2/5 · active`, not `TODO`, and a task paused for review reads
`waiting for alice`, not `PAUSED`.

A task is **ready** for you when it is `TODO` or `PAUSED`, everything it depends on is
`DONE`, it is assigned to nobody or to you, it has no open child, and no ancestor is
claimed or assigned. `tasks ready` orders them by effective priority, then `PAUSED`
before `TODO` — finishing beats starting — then oldest first. An empty answer is a
successful query, not an error.

## Priority

`priority` is one of `urgent`, `high`, `normal` (the default) or `low`. A task's
**effective priority** is the highest of its own and its ancestors': an urgent epic makes
its parts urgent without a write to each of them, and overviews label them
`urgent (inherited)`. Nobody sets a priority by default, so the queue runs on the
started-first rule alone; a level set by a person is a deliberate jump of the queue.

## The start and finish gates

A task has two gates, and both fail safe.

- **The start gate** — `depends_on`. A task may be claimed, or done, only when every
  reference resolves to a live task that is `DONE`. Checked by `claim` and `done`;
  `--force` can override it.
- **The finish gate** — the task's children and `finishes_after`. A task may be done
  only when every live child, and every task in `finishes_after`, is `DONE` or
  `CANCELLED`. Checked by `done`; nothing overrides it.

Anything that cannot be resolved confidently — a missing task, an archived one, a
manifest that does not parse, a project that is not checked out — counts as blocking.
A typo can delay work; it can never make an agent start something prematurely.

Cancelled work never satisfies a dependency: nothing can be built on it. A task that
depends on a cancelled one is not blocked but **stranded** — waiting cannot open the
gate. `cancel` lists those dependents in its result, overviews show
`blocked by A (cancelled)`, and a person decides: cancel the dependent too, remove the
reference, or point it at whatever now does that work. See
[gates](/docs/reference/gates).

## Containment

A parent owns its subtree, and decisions taken on it are written into every task
beneath it, so every file tells the truth about its own task.

- `defer` moves every open descendant to `BACKLOG`, keeping `state.md` and assignees.
- `schedule` brings every `BACKLOG` descendant back: `PAUSED` where a `state.md` exists,
  `TODO` elsewhere.
- `cancel` cancels every open descendant and clears their claims.
- `done` never cascades — a parent is done only when its children are — and neither
  does `reopen`.

Every open descendant of a `BACKLOG` task is `BACKLOG`: nothing beneath an unscheduled
epic can be scheduled, claimed or reopened past it. A cascade that would reach a live or
unknown claim is refused; one that reaches an orphaned claim supersedes it.

A claimed or assigned task **holds** its subtree: while an epic is being planned, or its
plan awaits approval, nothing beneath it is ready and `claim` on a child is refused. The
planner claims the epic, writes `design.md` and `plan.md`, creates the children — held —
and hands the epic to the approver; the approver's `unassign` releases them to whoever is
free.

## The resume point

`state.md` is the **resume point** of a task and the evidence that work started. Its
recommended shape is four sections — **Done**, **Verified**, **Open**, **Next** — with
_Open_ naming every uncommitted file and branch the work leaves behind.

The exit protocol is part of the contract, not advice:

- `pause` and `handoff` are refused while `state.md` is missing.
- `release` is refused while it exists: work that produced something is paused.
- `tasks state` writes it through the same fence as a transition, so a session whose
  claim was taken over learns of it before it overwrites the new claimant's file.
- `tasks session-check` verifies that every task the current session holds has one; a
  harness runs it at the end of every turn.
- The **freshness rule**: every turn in which the work progressed ends with `state.md`
  updated. The status stays `IN_PROGRESS` between turns.

The log is history and is never read on entry; the task's last entry — the note one
actor left for the next — rides along in `show`, `resume` and `mine`.

## Sessions and liveness

An **actor** is the name an action is recorded under: `--as`, else `TASKS_ACTOR`, else
the repository's git `user.name` or `user.email`, else the operating-system user. A
**session** is one run of an agent, named by a token: `--session`, else `TASKS_SESSION`.
A claim records both, and every log heading a session writes carries `s:<token>`.

Every command run with a session touches its heartbeat file under
`.tasks/.locks/sessions/`, and `tasks session-end` marks the session ended. A claim's
**liveness** follows:

| Liveness   | When                                                                                   |
| ---------- | -------------------------------------------------------------------------------------- |
| `live`     | the claim's session was active within `session_timeout_minutes` (30) and has not ended  |
| `orphaned` | the session went silent for longer, or said goodbye with `session-end`                  |
| `unknown`  | the claim has no session (a person at a terminal), or no heartbeat file exists for it   |

A live or unknown claim is protected: only its claimant — the same actor, in the same
session — may transition it. An orphaned claim protects nothing: the actor's next
session takes it over with an ordinary `claim`, and the log records which session was
superseded and when it was last seen. The superseded session, should it come back, gets
a conflict on its next write instead of overwriting the new claimant's work.

`--force` is the one override, always recorded in the log. It lifts the authorization
rules, the start gate, a live or unknown claim, and a hold — never the finish gate, the
`state.md` rules, a resolved parent, the `BACKLOG` invariant, a cycle, a reserved path,
or a required message.

## Projects

A tree may list the trees it works with under `projects:` in `config.yml`, by alias:

```yaml title=".tasks/config.yml"
version: 2
projects:
  backend: ../backend
  cli: ../tasks-cli
```

`backend:auth/token-schema` then addresses a task there, overviews span every listed
tree with foreign ids qualified by alias, and commands can write into listed trees —
each under that tree's own lock. A tree reached only by a relative path in a reference,
without being listed, is read-only. The usual layout is a dedicated tracker repository
that lists the product repositories; see the [projects guide](/docs/guides/projects).
